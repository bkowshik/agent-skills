# Speckit Auto

Run the entire speckit design-to-implementation pipeline from a single
command. You provide a feature description; the system runs specify, clarify,
plan, tasks, analyze, and implement in sequence -- making informed decisions
at every step so you are never interrupted.

## When to use

Use this skill when you have a feature idea and want to go from description
to working implementation without manually invoking each speckit step. This
is the "hands-free" mode for the speckit workflow.

**Prerequisites**: This skill requires the speckit command suite to be
installed in the host project (the `/speckit.*` commands in
`.claude/commands/`). It also requires a valid `.specify/` directory with
templates, scripts, and a project constitution.

## User input

The user provides a feature description as the command argument. This
description is passed through to the specify step unchanged.

**Examples:**
- `/speckit-auto Add user authentication with OAuth2`
- `/speckit-auto Create a dashboard for analytics`
- `/speckit-auto Fix payment processing timeout bug`

If no description is provided, stop and ask the user to provide one. Do not
proceed with an empty description.

## Workflow

### Precondition checks

Before starting the pipeline, verify these conditions. If any fail, stop
and report the issue to the user.

1. **Clean working directory**: Run `git status --porcelain`. If any output
   is returned, stop and tell the user to commit or stash their changes
   first. A pipeline run on a dirty tree risks mixing unrelated changes.

2. **No existing branch**: The specify step will create a new feature
   branch. If a branch already exists for this feature (detected during
   specify), stop and tell the user to either resume the existing pipeline
   manually or delete the branch to start fresh.

**Global rule -- no git commits**: Throughout the entire pipeline, do not
create any git commits. All artifacts and implementation code are written
to disk but remain uncommitted. The user reviews and commits at their
discretion after the pipeline completes.

### Progress reporting

At the start of each step, output a progress header:

```
## Step N/6: [Step Name]
Starting [brief description]...
```

At the end of each step, output a completion or failure line:

```
✓ [Step Name] complete. [Brief result summary]
```

Or on failure:

```
✗ [Step Name] failed. [Brief error summary]
```

This gives the user clear visibility into which step is running and whether
earlier steps succeeded.

### Failure handling

If any step fails (produces an error, fails validation, or cannot complete
after its built-in retry logic), do the following:

1. Output the failure line with the step name and error details.
2. List all artifacts generated by previous steps that are preserved on disk.
3. Output the exact speckit command the user can run to resume from the
   failed step.
4. Stop the pipeline. Do not proceed to the next step.

**Format:**

```
Pipeline halted at: [Step Name] (step N/6)
Error: [Error details]
Artifacts preserved: [comma-separated list of files]
Resume with: /speckit.[step-name]
```

Since each speckit command writes artifacts to disk as it runs, all
previously completed work is naturally preserved on failure.

### Step 1: Specify

Invoke the speckit specify command with the user's feature description.
Pass the description through unchanged -- do not summarize or rephrase it.

The specify step will:
- Generate a short name for the feature
- Create a new feature branch
- Write the initial spec.md

After invocation, verify that the spec file was created in the feature's
specs directory. If the specify step fails (e.g., description too vague),
follow the failure handling procedure.

### Step 2: Clarify

Invoke the speckit clarify command to scan the spec for ambiguities.

**Auto-resolve mode**: For each clarification question the clarify step
would normally ask the user, instead select the recommended option or
generate a best-practice answer. Do not wait for user input. For each
auto-resolved decision:

- Choose the option that best aligns with project context, industry
  standards, and the project constitution
- If a recommended option is presented, select it
- If no recommendation is given, make an informed choice and briefly
  explain the reasoning

Each auto-resolved decision will be documented in the spec's Clarifications
section by the clarify command itself.

After invocation, verify that the spec was updated. If clarify fails,
follow the failure handling procedure.

### Step 3: Plan

Invoke the speckit plan command to generate the implementation plan.

The plan step will:
- Generate plan.md with architecture and technical decisions
- Generate research.md with research findings
- Generate data-model.md with entity definitions
- Generate quickstart.md with test scenarios
- Optionally generate contracts/ for interface definitions

After invocation, verify that plan.md was created. If the plan step fails,
follow the failure handling procedure.

### Step 4: Tasks

Invoke the speckit tasks command to generate the task breakdown.

The tasks step will:
- Generate tasks.md with dependency-ordered implementation tasks
- Organize tasks by user story and phase

After invocation, verify that tasks.md was created. If the tasks step
fails, follow the failure handling procedure.

### Step 5: Analyze

Invoke the speckit analyze command to check cross-artifact consistency.

The analyze step is read-only -- it reports issues but does not fix them.
After receiving the analysis report:

- **If no issues found**: Proceed to the next step.
- **If issues found**: For each inconsistency, determine which artifact(s)
  need updating, make the fix directly in the affected file(s), then
  re-run the analyze command once.
  - If the second run finds no issues: Proceed to the next step.
  - If issues persist after the fix attempt: Follow the failure handling
    procedure. Report the remaining inconsistencies and tell the user to
    resolve them manually before running the implement step.

### Step 6: Implement

Invoke the speckit implement command to execute the implementation plan.

The implement step will:
- Read tasks.md and execute each task in order
- Write implementation code to the repository
- Mark completed tasks in tasks.md

**Reminder**: Do not create any git commits during implementation. All
code is written to disk but remains uncommitted.

After invocation, verify that implementation tasks were completed. If the
implement step fails, follow the failure handling procedure.

### Completion summary

After all 6 steps complete successfully, output a final summary:

```
## Pipeline Complete
Branch: [feature-branch-name]
Artifacts:
  - specs/[feature]/spec.md
  - specs/[feature]/plan.md
  - specs/[feature]/research.md
  - specs/[feature]/data-model.md
  - specs/[feature]/quickstart.md
  - specs/[feature]/tasks.md
Implementation: [list of created/modified source files]
No git commits were made. Review changes with `git status` and `git diff`.
```

## Edge cases

- **Empty or vague description**: If the user provides no description or a
  description too vague to generate a meaningful spec (e.g., "make it
  better"), the specify step will refuse to proceed. Report this to the
  user and ask for a more detailed description.

- **Uncommitted changes**: The precondition check catches this before any
  steps run. Tell the user to commit or stash their changes first.

- **Existing branch/artifacts**: If the specify step detects an existing
  branch for the same feature, it will report the conflict. Tell the user
  to either resume the existing pipeline manually (using the individual
  speckit commands) or delete the branch to start fresh.

- **Analyze auto-fix failure**: If the analyze step finds inconsistencies
  that cannot be resolved after one auto-fix attempt, the pipeline halts.
  The user should review the reported inconsistencies, manually fix the
  artifacts, and run the analyze and implement steps individually.

- **Long-running execution**: The pipeline runs 6 sequential steps, each
  of which may take significant time. The progress reporting ensures the
  user can track where the pipeline is at any point.

## Example

A user wants to add a search feature to their project:

```
/speckit-auto Add full-text search with filters and pagination
```

The pipeline runs:

```
## Step 1/6: Specify
Starting specification generation...
✓ Specify complete. Created specs/009-full-text-search/spec.md

## Step 2/6: Clarify
Starting ambiguity scan...
Auto-resolved 2 clarifications (documented in Clarifications section)
✓ Clarify complete. Updated specs/009-full-text-search/spec.md

## Step 3/6: Plan
Starting implementation planning...
✓ Plan complete. Created plan.md, research.md, data-model.md, quickstart.md

## Step 4/6: Tasks
Starting task generation...
✓ Tasks complete. Created specs/009-full-text-search/tasks.md (18 tasks)

## Step 5/6: Analyze
Starting cross-artifact consistency check...
✓ Analyze complete. No inconsistencies found.

## Step 6/6: Implement
Starting implementation...
✓ Implement complete. 18/18 tasks finished.

## Pipeline Complete
Branch: 009-full-text-search
Artifacts:
  - specs/009-full-text-search/spec.md
  - specs/009-full-text-search/plan.md
  - specs/009-full-text-search/research.md
  - specs/009-full-text-search/data-model.md
  - specs/009-full-text-search/quickstart.md
  - specs/009-full-text-search/tasks.md
Implementation: src/models/search.py, src/services/search_service.py, ...
No git commits were made. Review changes with `git status` and `git diff`.
```

If the analyze step had found issues:

```
## Step 5/6: Analyze
Starting cross-artifact consistency check...
✗ Analyze found 1 inconsistency. Attempting auto-fix...
  - Fixed: plan.md referenced "SearchIndex" entity not in data-model.md
✓ Analyze complete after auto-fix. No remaining issues.
```
